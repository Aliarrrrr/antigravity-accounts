# Antigravity Profile Hub architecture

## Scope and evidence
Windows local desktop profile manager for N profiles. Authentication remains entirely in Google's app. Read CAPABILITY_REPORT.md before changing the driver. Antigravity Desktop 2.12.2 is not the old VS Code-derived IDE. Independent user-data alone is insufficient because desktop also resolves .gemini from the process home. Manual acceptance also showed directory separation does not isolate concurrent Google accounts under one Windows user, so only one Antigravity root may run at a time.

## Stack and boundaries
C# / .NET 10 LTS; WPF native UI; dependency-light console CLI. Core has no WPF dependency. JSON persistence via System.Text.Json. Windows process adapter may use System.Management for process metadata. Unit tests use xUnit if restore is available; otherwise a deterministic console test runner with failing exit status is acceptable. No server, database service, Electron shell or cloud backend.

Projects: src/AGProfileHub.Core, src/AGProfileHub.Cli (agprofile), src/AGProfileHub.Gui, tests/AGProfileHub.Tests. Presentation calls HubService; only IAntigravityDriver builds vendor arguments/environment. Domain records: Profile, Settings, CapabilityReport, ProfileRuntime, ProcessIdentity. Profile IDs are immutable UUIDs; names are editable and never become paths.

## Storage
Default root: LocalApplicationData/AntigravityProfileHub. config/profiles.json and settings.json contain schemaVersion=1; profiles/<uuid>/{user-data,home,roaming,local,temp}; runtime/state; runtime/locks; logs; cache. A fixed `global-launch-state` directory under the current Windows user's LocalApplicationData holds the cross-data-root launch lock and short-lived launch barrier. User workspaces stay outside the managed profile root. No copies of existing .gemini, cookies, credentials or old IDE data.

Atomic same-directory temporary writes with replace/backup, process-wide file locks for config read-modify-write, and per-profile locks for launch/stop/restart. Reject unsupported future schemas without overwriting. Do not silently recover corrupt config to an empty profile set. All managed paths are computed from validated UUIDs, canonicalized, and checked for reparse points. Remove unregisters only; destructive purge is deferred from MVP.

## Driver
Discover explicit setting then standard install paths. Read executable file version without launching. The Desktop 2.12.2 driver launches through Windows CreateProcess with quoted --user-data-dir=<absolute path>, a dedicated environment block, and no inherited handles. Child-only USERPROFILE/HOME/HOMEDRIVE/HOMEPATH/APPDATA/LOCALAPPDATA/TEMP/TMP overrides isolate paths. Never modify the caller's environment or Windows user. This is path separation, not a security sandbox; the same Windows account can access both directories. Tool children inherit the synthetic home and will not automatically see existing SSH/Git/tool settings.

Do not claim --profile, --extensions-dir or positional workspace support: current desktop has no demonstrated IDE CLI contract. Store workspace metadata; refuse an unsupported launch-with-workspace operation clearly until verified. Do not mutate Antigravity's internal project configuration to compensate. CLI/headless identity is out of scope.

## Processes and recovery
Identity = PID + creation timestamp + canonical executable path + exact parsed user-data argument for the root. Never trust PID alone, substring matches, executable name alone, or stale runtime JSON. Reconcile live process roots at startup and each action; enumerate descendants with creation-time checks. Record owned snapshots without storing child command lines (vendor LS command lines include ephemeral bridge/CSRF secrets). Repeated launch focuses an existing window or reports already running. One per-user file lock serializes every Hub data root. Before CreateProcess, an atomic barrier records the launch reservation; after creation it records the expected process identity and is removed only after runtime state is committed. Delayed process discovery, cancellation, invalid barrier data and state-write failures therefore block new launches. The live root scan rejects any detected root of the configured executable, including a root not registered in the current Hub data root. A copy at another executable path is outside that scan, although Hub-managed launches still share the per-user lock and pending barrier. Graceful window close first, bounded wait, then only verified owned processes; never taskkill by name. Orphaned or unverifiable children produce unknown state rather than broad termination. Hub GUI singleton is independent of process locks; CLI shortcuts can run concurrently but cannot bypass the Hub-managed gate.

ProcessSupervisor owns lifecycle ordering, locks, launch-barrier recovery, retries and logging. ProcessOwnershipResolver centralizes the security-critical live-snapshot rules for root classification, identity matching, status resolution and deepest-first descendant ordering.

## Compatibility
The verified experimental directory/process strategy is pinned to Desktop 2.12.2. Each launch reads the installed file version; unknown versions are refused before launch directories are created. Settings reserve exact-version/path evidence fields, but current local probe reports are separate artifacts rather than automatically imported attestations. Doctor reads configuration, file-version and process metadata. Dynamic probing uses scripts/Probe-Antigravity.ps1; there is no doctor --probe command. Manual acceptance found concurrent Google account isolation incompatible on this version, and changing the configured executable clears saved authentication attestation fields.

## Shortcuts
DesktopShortcut writes Windows .lnk files via WScript.Shell, then moves the unique temporary link into place without overwriting existing files. Target is the packaged CLI executable; arguments contain the absolute Hub data root and immutable profile UUID. A rename preserves the old link's behavior. Moving the package requires recreating links. GUI and CLI share this service; no vendor launch arguments are duplicated in shortcuts. Tray integration remains deferred.

## Logging and UI
Allowlist structured event fields: timestamp, operation, profileId, antigravityVersion, sanitized command template, processId, result, error code. Never ingest vendor stdout/logs or child command lines. Drain/discard vendor output. Do not serialize arbitrary exception contents containing launch secrets. GUI cards/table: Profile, Status, Workspace, actions; create/rename/remove registration, launch/stop/restart, all actions, doctor, settings, open-data, logs. Desktop shortcuts call agprofile launch UUID; tray is an enhancement. CLI JSON is the first automation interface.
