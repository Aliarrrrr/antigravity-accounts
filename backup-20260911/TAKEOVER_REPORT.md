# 项目接管分析 — 2026-09-09

## 结论

核心功能这次能够跑通，不是因为目录隔离“终于调对了”，而是因为定位到了目录之外的唯一共享认证键，并针对 Sandboxie 的真实读写语义补上了隔离域本地占位。此前失败的方案大多解决了进程、目录、端口或 OAuth 表象，却没有改变 language server 最终读取的 Windows Credential Manager 条目，因此后登录账号必然覆盖前一个。

## 为什么新方案成功

1. **找到决定性共享状态。** language server 使用固定目标名 `gemini:antigravity`，不随 `--user-data-dir`、`HOME`、`--app_data_dir` 或 Profile UUID 变化。
2. **解释了所有旧现象。** A/B 目录和进程确实独立，但都读取同一个宿主凭据；所以顺序重启看似正常，并发后却一起变成最后登录账号。
3. **理解了 Sandboxie 的不对称语义。** 盒内写入会被隔离，但盒内缺少条目时读取会回退到宿主。仅设置 `OpenCredentials=n` 不能阻止这个回退。
4. **用同名本地条目阻断回退。** 在全新盒内先写入无效占位后，读取命中盒内条目；vendor 解析失败后走自身文件存储降级路径，后续真实登录保存在该隔离域。
5. **验收覆盖了因果链。** A/B/宿主三域条目元数据不同；A/B 不同账号可并发；重启 A 后 A 保持、B 进程不变；宿主条目不变。

## 对过去失败方案的反思

| 方案/判断 | 为什么没跑通 | 应吸取的教训 |
|---|---|---|
| 只隔离 Electron user-data 和 HOME | 只覆盖文件路径，没有覆盖固定 Credential Manager 键 | “目录创建独立”只能证明路径隔离，不能外推为身份隔离 |
| 把问题归因于 OAuth 协议回调或端口 | LS 使用各自动态本地端口，端口和 CSRF 已独立；真正共享发生在 token 读取 | 优先追踪最终持久化状态，而不是停在流程入口 |
| 标准 Sandboxie + `OpenCredentials=n` | 盒内未命中时仍回退宿主凭据 | 必须分别验证 read/write/delete 和空盒/已有盒，不可从配置名推断行为 |
| 第一轮 synthetic credential 矩阵 | 宿主 `cmdkey` 写入未被可靠确认，产生“读不到即隔离”的假阳性 | 每个测试前置条件都要有独立正向断言；工具退出/空输出不能等同成功 |
| Privacy Mode | 本机无 supporter certificate，约五分钟后终止 | 试验能力、授权条件和可分发依赖必须一起纳入产品判断 |
| 先增加串行门禁和 GUI 完整度 | 提高了安全性和可交付性，但没有解决原始并发目标 | 缓解措施必须清楚标注为降级路径，不能替代核心验收 |

## 本轮接管发现的产品化缺口

- 隔离逻辑只散落在 CLI，GUI、restart、status 和 shortcuts 没有统一走它。
- 混合 `launch-all` 会先启动隔离 Profile，再把所有 Profile 送入旧串行路径，存在重复/非隔离启动风险。
- shim 任意失败退出码仍会被记录为 `KeyringClaimed=true`。
- 宿主可直接运行强制 shim，存在覆盖真实宿主登录条目的风险。
- 两个 Profile 可绑定同一个盒，隔离状态采用非原子、无锁写入。
- 包中不含两份必需的 Sandboxie 配置脚本，manifest 仍宣称认证不兼容。
- 当前默认 A/B 的直写规则仍指向旧验收目录；身份隔离通过不等于项目文件可用性完成。

这些缺口已在 Core、CLI、GUI、测试、Doctor、脚本和打包配置中逐项收口。仍需用户参与的只有系统级直写配置及真实账号登出/工作区行为验收。
