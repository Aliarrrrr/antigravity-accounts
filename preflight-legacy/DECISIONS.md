# Decisions

- ADR-001 accepted: .NET 10 LTS + WPF for native Windows, Core + CLI first. User-local SDK installation avoids administrator changes.
- ADR-002 accepted: schema-versioned JSON, atomic replace/backups, locking; reject unknown future schemas.
- ADR-003 accepted: root ownership requires PID, start time, executable, exact user-data arg; descendants cannot be killed by executable name. Stale runtime files are hints only.
- ADR-004 experimental: Desktop 2.12.2 needs independent process home AND user-data. Old IDE flags alone are not adequate. Local dynamic probe observed separate roots/backends/state directories. Auth remains manual. No new Windows user or token manipulation.
- ADR-005 accepted: shortcuts invoke CLI with immutable UUID; no duplicated vendor launch construction.
- ADR-006 accepted: workspace stored as metadata until a supported Desktop launch mechanism is verified. Never pretend an ignored positional argument works. GUI must communicate this limitation.
- ADR-007 accepted: remove unregisters; no purge for MVP. No import/copy of existing identities.
- ADR-008 accepted: omit arbitrary launch arguments initially; they could override isolation or leak secrets. Log allowlisted templates only; discard vendor output.
- ADR-009 accepted: experimental delivery can continue before human OAuth testing, but full functional acceptance cannot be marked complete. Agent Safe worktrees, tray, CLI identity are later work.
- ADR-010 accepted: manual validation on Desktop 2.12.2 showed concurrent profiles resolving to the Google account signed in later. The Hub preserves profile data, makes no credential changes, and blocks a second Antigravity root instead of claiming separate-account support. Real concurrent multi-account support requires an official profile-scoped authentication contract or a separate Windows identity boundary.
- ADR-011 accepted: Installed-app review found no supported same-Windows-user override for Desktop 2.12.2's fixed credential identity. Directory-only launchers, token switchers and standard Sandboxie are not authentication backends. Do not add a backend schema or relax DirectSerial gates before an external OS-user proof proves interactive windows, owner/session recovery, OAuth routing and real A/B account isolation. The superseded research notes remain local-only.
- ADR-012 accepted, superseding ADR-010/011's closed-backend conclusion: metadata-only inspection identified the fixed credential target `gemini:antigravity`; Sandboxie boxed reads fall through only while the box lacks a local same-name entry. A never-signed-in box may receive an invalid placeholder that blocks fall-through, after which the official login flow owns isolated state. This exact mechanism passed real A/B concurrent-account and restart acceptance. It never reads/copies a token and must fail outside a confirmed Sandboxie process.
- ADR-013 accepted: `HubService` is the sole lifecycle router. Prepared Profiles use dedicated boxes; unprepared Profiles retain the serial direct fallback. Batch launch is fail-closed and all-or-nothing at preflight. Isolation mappings use atomic schema-checked storage and unique box ownership. Workspace/Profile direct-write readiness is a separate gate surfaced by Doctor/UI, not evidence inferred from authentication success.
- ADR-014 accepted: the isolation backend is an **additive, optional field** instead of a schema-version bump. Bumping the global `SchemaVersions.Current` would have invalidated runtime records, launch barriers, isolation state and elevation payloads at once; an absent field simply deserialises to the record's default, so no migration is needed. Unknown future schemas are still rejected, and undefined enum values fail closed. Known hazard: an older build reading `processLocal` treats the Profile as Sandboxie, so the field is only written when it differs from the record's default.
- ADR-015 accepted: **process-local is the default backend for newly created Profiles** (no sandbox product, no elevation, no credential shim, no direct-write rules). Sandboxie stays available as an explicit legacy backend so profiles that already own a box keep working. A process-local launch must prove in the language server's own log that it moved to the file token store; otherwise the instance is stopped and the launch fails with `isolation_scope_unverified`. The vendor `antigravity://` callback is routed to the Profile that is waiting for it, because without a sandbox the single global registration cannot tell them apart; registering points the scheme at the Hub and keeps the previous handler for restore.
- ADR-016 accepted: Sandboxie is removed. The credential guarantee now rests on per-Profile file token stores plus a fail-closed launch assertion over the language server's own log, instead of registry virtualisation and a shim that claimed the vendor credential name. The recorded legacy backend value resolves to the same process-local scope. Deep-link callbacks route through an explicit registration verb that backs up and can restore the previous handler. Positional records that gain an optional backend-like field must declare it as a defaulted constructor parameter: source-generated JSON skips absent properties without running property initialisers, so an init-only default silently deserialises as the zero value.
